# NorthStar Churn Model Security, Privacy, and Compliance Assessment

**Scope.** This assessment covers the Lab 5 real-time SageMaker churn endpoint and the Lab 1–4 data path that supports it: S3 raw, processed, features, artifacts, and data-capture prefixes; Glue transforms; SageMaker Feature Store; model training and registry; endpoint invocation; and operational logs. It describes project configuration visible in this repository and Lab 5 evidence. It does not claim that the course deployment is a certified production environment.

## 3b. Data classification and controls

Engineered customer features include recency, tenure, purchase frequencies, spend, lifetime value, basket size, category diversity, online/store ratio, loyalty tier, churn-risk score, and churn label. The inspected schema does not show names, email addresses, phone numbers, or street addresses. A stable customer identifier plus purchase history can still be linkable and sensitive; do not treat it as anonymous. ## 4. Privacy and compliance assessment

|:---|:---|:---|

| Processed transactions | The transaction fields after type casting and validation, including `customer_id`. | Clean input for feature engineering. Cleaning does not make the records anonymous. |

The data owner must confirm provenance and the fields present in the actual source files before representing this as a real-customer system.

### Lawful basis

**Chosen basis for this assessment: legitimate interests (GDPR Article 6(1)(f)).** NorthStar has a legitimate interest in understanding which customers may stop purchasing so it can offer relevant retention support and improve service. Purchase history is necessary to calculate the project’s recency, frequency, and spend features; the model does not need names, contact details, full payment credentials, or raw transaction IDs as model inputs. The balancing test should consider customers’ reasonable expectations, the intrusiveness of profiling, and possible effects of offers based on a score. Article 6(1)(f) requires a legitimate interest, necessity, and a balancing test; the [EDPB guidance](https://www.edpb.europa.eu/system/files/2024-10/edpb_summary_202401_legitimateinterest_en.pdf) describes these steps. Safeguards are purpose limitation, transparency in the privacy notice, access controls, short retention, human review of consequential actions, and honoring applicable objection rights. Customers may object to processing based on legitimate interests, including profiling; objections to direct marketing must be honored for that processing under [GDPR Article 21](https://eur-lex.europa.eu/eli/reg/2016/679/oj/eng/). The churn score must not be used as the sole basis for a decision with significant effects. The organization must document a legitimate-interests assessment and confirm that this basis fits the actual jurisdiction and use; this is the selected basis for the lab scenario, not a claim that legal review has already approved it.

### Data minimization

The project considered raw purchase date, order value, item count, payment method, channel, store ID, product category, transaction ID, and customer ID. The model trains on eleven aggregate features: days since last purchase, customer tenure, purchase frequency over 30/90/180 days, average order value, 90-day spend, lifetime value, average basket size, category diversity, and online-to-store ratio. It excludes names/contact details, full payment credentials, transaction ID, raw transaction rows, payment method, and exact store ID because they are not model features. `customer_id` is retained only as a join/record identifier in intermediate data and Feature Store; it is not one of the eleven model inputs. `churn_label` is the training target, not an input; `loyalty_tier` is used for evaluation slices, not as a model feature. The lab endpoint captures 100% of request and response payloads, so the serving payload should contain only the eleven features, with no direct identifier. Limit capture to the lab evidence/debugging period and restrict reads. Apply raw and capture lifecycle rules, and define current-object retention for processed and feature data before production.

### Right to erasure workflow

For a verified request concerning `customer_id = C00123456`, follow this workflow under the organization’s approved GDPR process. Record the request, deadline, scope, and any documented exception or legal hold.

1. **Raw S3:** locate objects in `raw/` and `processed/` containing `C00123456`. Rewrite each affected dataset without that customer and replace/delete the original objects. Because S3 versioning is enabled, an authorized operator with `s3:DeleteObjectVersion` must also permanently delete relevant noncurrent versions where policy permits; the current `DataEngineer` policy has `s3:DeleteObject` but not `s3:DeleteObjectVersion`. A delete marker alone leaves old data recoverable. Check exports, backups, and holds.
2. **Feature Store:** an authorized operator with `sagemaker:DeleteRecord` deletes the online record using Feature Store `DeleteRecord` for record identifier `C00123456`. The current `DataEngineer` policy does not grant `DeleteRecord`, so a scoped permission or designated privacy-operations role is needed. For the offline store, locate its S3/Parquet records and rewrite or compact affected files without the customer, update the catalog if needed, and delete superseded S3 objects and versions where permitted. Verify the online lookup and an offline query return no record. Offline history is append-oriented, so deleting the current online record alone is insufficient.
3. **Model training data and weights:** remove the customer from the curated feature/training/validation datasets and regenerate the training input. Retrain and evaluate a replacement model, then register and deploy it under normal approval; retire old packages/artifacts if the approved policy requires removal of their influence. There is no row-level delete operation for information already incorporated into model weights.
4. **Inference logs:** search request/response capture objects and any application or CloudWatch logs/exports for `C00123456` and linked records. Delete matching S3 capture objects and noncurrent versions where permitted; apply the approved log deletion/retention process to other copies. The current lab payload uses only model features, so the ID should not be in it; verify this rather than assuming it. Stop capturing unnecessary fields in future requests.

**Hardest step: removing the customer’s influence from trained model weights.** Removing a source row does not reverse what training encoded in the parameters. The reliable project-level remedy is to rebuild the training data without the customer, retrain, evaluate and approve a replacement, then retire affected artifacts and deployments. That takes more work than deleting a row or Feature Store record, and the previous model package may need to remain temporarily for a documented rollback or legal hold.

### Compliance posture and open decisions

The project demonstrates private S3 access controls, IAM roles, versioning, encryption at rest with SSE-S3, lifecycle policies for selected prefixes, IAM-authorized SageMaker invocation, and a CloudWatch latency alarm. These controls do not establish regulatory compliance or a complete enterprise security program. Before production use with real customer data, confirm data provenance and jurisdiction, role and policy scope, online/offline Feature Store encryption and retention, log and audit retention, deletion handling for versions/backups, endpoint caller authorization and rate controls, incident response, and privacy review of churn-score use. No external vendor sharing or public product-catalog publishing is configured for this Lab 5 deployment.
